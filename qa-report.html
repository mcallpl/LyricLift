✓ FixedCritical

YouTube URL extraction fails — "Video unavailable"

app.py:84–98

Ran the app's exact yt-dlp download command against a known-stable YouTube test video. It failed immediately:

WARNING: [youtube] No supported JavaScript runtime could be found. Only deno is enabled by
default... YouTube extraction without a JS runtime has been deprecated...
ERROR: [youtube] BaW_jenozKc: Video unavailable

YouTube now requires a JS runtime (deno or node, passed via --js-runtimes) for reliable extraction — yt-dlp doesn't auto-detect one. Neither app.py nor extract.php pass this flag, and no JS runtime is installed alongside the app. YouTube is the app's flagship, most-advertised input method — this is the most likely explanation for "it doesn't work" reports.

✓ Resolved 2026-07-01

Added a detect_js_runtime() helper to app.py that finds an installed runtime (deno → node → bun, overridable via LYRICLIFT_JS_RUNTIME) and passes --js-runtimes to the yt-dlp command. When no runtime is found, the error message now says so explicitly instead of a generic failure, and the yt-dlp stderr is logged for debugging.

Verified: a live YouTube URL now transcribes end-to-end through the running app — returned correct SRT text with timestamps. (The original test video ID was genuinely deleted; a known-good video confirmed the fix.)

⚠ Production reality (verified live 2026-07-02)

Deployed to empire-command and tested against https://lyriclift.peoplestar.com. node is installed, so the JS-runtime fix works — but YouTube still blocks the download because the server is on a datacenter IP (HTTP 429 + "Sign in to confirm you're not a bot"). This is YouTube's anti-VPS bot check, not a code issue — the same request succeeds from a residential IP.

Mitigations added: the app now (1) auto-uses a youtube_cookies.txt file if present (drop in a logged-in session export to make YouTube work — see DEPLOY_FLASK.md §3c), and (2) returns a clear "please upload the file directly instead" message when a download is bot-blocked. File upload → transcription is fully working on production and is the reliable path.

✓ FixedCritical

The documented SSL fix (PYTHONHTTPSVERIFY=0) does not work

app.py:130 · extract.php background script (~line 127) · README.md § Troubleshooting

README lists this as an already-applied fix for Whisper's SSL error. Reproduced it directly: ran the exact whisper model-download call with PYTHONHTTPSVERIFY=0 set exactly as app.py sets it, and it still failed —

ssl.SSLCertVerificationError: [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed:
self signed certificate in certificate chain

If the model cache is ever cleared, a different model size is used, or the server hits any TLS interception/certificate issue, transcription fails immediately with the app's generic "Transcription failed" message — giving no signal that matches the README's own troubleshooting advice.

✓ Resolved 2026-07-02

Removed the ineffective PYTHONHTTPSVERIFY=0. Added ensure_whisper_model() which pre-fetches the model into the cache before transcription using a proper CA bundle (certifi, added to requirements.txt; falls back to system certs) and verifies its SHA-256 checksum — so the transcription subprocess never has to make a network/TLS call. The model is also preloaded at startup (surfacing any problem in the logs at boot), and the whisper subprocess now gets SSL_CERT_FILE/REQUESTS_CA_BUNDLE pointed at the good bundle as a fallback. When the model genuinely can't be obtained, the user now sees a clear "model unavailable" message instead of a generic failure.

Verified: (1) model present → transcribes correctly; (2) model missing + download blocked → job returns the clear "Speech recognition model is unavailable" message and the app stays alive (no crash); (3) startup logs a warning when the model can't be preloaded.

Recommended for production

Bake the model file into the deploy (.cache/whisper/tiny.pt) so runtime never needs the network at all. Note: on this dev machine the download still fails because of a local corporate TLS-intercepting proxy (a self-signed root not in any bundle) — that's an environment artifact, not the app; a normal server with ca-certificates + certifi downloads fine.

Broken shell-escaping in extract.php's background script

extract.php (~line 97)
$dlCmd = 'python3 -m yt_dlp ... -o "' . $audioPath . '" "' . escapeshellarg($url) . '" 2>&1';

escapeshellarg() already wraps its output in single quotes for shell safety — nesting that inside an additional pair of double quotes neutralizes the escaping (single quotes are literal characters inside double quotes), so yt-dlp receives a malformed URL with literal quote characters stuck to it. Only matters if the PHP path is ever reactivated, but it's a real, verifiable bug sitting in the repo today.

✓ Resolved 2026-07-01

Moot — extract.php was deleted with the dead PHP backend (Critical #2). The live Flask path uses a proper argument list (subprocess.run([...])) with no shell, so this class of quoting bug can't occur there.

A low no-speech threshold plus the smallest Whisper model is a known combination for occasional hallucinated text on silence. This is the documented speed/accuracy tradeoff of using the "tiny" model, not a code defect — flagged for awareness, not as a fix item.

Left as-is — a tradeoff decision, not a bug

The aggressive --no_speech_threshold 0.1 was almost certainly set on purpose to reduce false "No speech detected" errors; raising it or moving to a larger model trades speed for fewer hallucinations. That's a product call, so it's left unchanged pending your preference. If you want, I can bump the threshold toward the default (0.6) or switch to the base/small model.

✓ FixedHigh

Uploading a file with a non-ASCII name returned HTTP 500

app.py:397–398 (upload handler)

The upload handler derived the extension from secure_filename(file.filename). For any non-Latin basename — Пример.mp3, 日本語.mp4, 音楽.mp3 — secure_filename strips the name down to just "mp3" (no dot), so .rsplit('.',1)[1] threw IndexError → caught by the generic handler → HTTP 500 "list index out of range." The extension check passed on the raw name, so any international user with a normally-named file simply couldn't upload.

✓ Resolved 2026-07-02

Take the extension from the original filename (already validated against the whitelist by allowed_file) and dropped secure_filename entirely — it was providing no safety here since the saved file is named after the safe job_id, not the user's name. Verified: reproduced the 500 with Пример.mp3, then confirmed the same upload now returns 202 and transcribes to the correct text; uppercase (.MP3) and multi-dot (my.song.final.mp3) names also work, and a no-extension file is still cleanly rejected with 400.

✓ FixedMedium

The cleanup sweeper could delete a still-running long job mid-transcription

app.py — cleanup_old_jobs vs. run_transcription_job

cleanup_old_jobs() deletes files older than the 6-hour TTL by mtime, and it now runs on a timer. But a job's status-file mtime is only written at each state change — it's frozen during the (possibly multi-hour) Whisper run. The app explicitly advertises hour-long jobs and the frontend polls for up to 12 hours, so a transcription running past 6h would have its status file (and input audio) swept out from under it → /status starts returning 404 → the user sees "job not found" even though it's still processing.

✓ Resolved 2026-07-02

Added a per-job heartbeat (start_job_heartbeat) that bumps the status file's mtime every 5 minutes while the job is alive and stops in the job's finally block. Live jobs stay fresh so the sweeper never touches them; a crashed/orphaned job stops heartbeating and still ages out normally. Verified: with a shortened TTL, a heartbeating job survived every sweep past its TTL, while a job whose heartbeat was stopped was correctly swept — and a normal job still completes and cleans up with no leftover files.

✓ FixedMedium

requirements.txt omitted the two core processing dependencies

requirements.txt

The app shells out to python3 -m yt_dlp and python3 -m whisper, but requirements.txt listed only Flask/Werkzeug/gunicorn/certifi. A fresh host provisioned with pip install -r requirements.txt would have neither tool — so every download and every transcription would fail at the subprocess.

✓ Resolved 2026-07-02

Added yt-dlp and openai-whisper to requirements.txt, with comments noting whisper is heavy (pulls torch) and that ffmpeg is still a required system package. yt-dlp is intentionally left unpinned so it stays current with YouTube changes.

✓ FixedLow

Two gunicorn workers could corrupt a cold-start model download

app.py — ensure_whisper_model

The systemd unit runs --workers 2, and each worker runs the model pre-fetch at import. The download used a fixed temp path (tiny.pt.download), so on a first-ever startup with no cached model, both workers could write the same temp file concurrently → corrupted download → checksum mismatch → model flagged unavailable.

✓ Resolved 2026-07-02

The download temp file is now per-process (tiny.pt.<pid>.download), so concurrent workers can't clobber each other; the checksum-verified os.replace into the final path stays atomic. (Not using gunicorn --preload on purpose — it would run module-level thread starts in the master, and threads don't survive fork, which would silently disable the cleanup timer in workers.)
